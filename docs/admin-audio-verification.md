3. **Performance changes.** Batched, parallel summary queries replace the Books N+1 path. Books/Shows list and chapter-list queries omit manuscript/transcript bodies; detail editors still load full content. A layout-owned, per-user memory cache deduplicates reads, expires after one minute, and invalidates after create/update/delete. It resets on account changes. Stale in-flight reads cannot replace a newer mutation snapshot. Dialog code loads on demand. The persistent navigation and route loading state remain available during data loading. Authorization memoization is confined to a React server request, with no persistent permission cache. Missing transcript-column capability is remembered for at most one minute, avoiding repeated failed queries while allowing migrations to take effect. Books/Shows summary queries have a 1,000-row bound; pagination beyond that bound remains a future requirement. Current data: 10 books, 86 chapters, 19 shows, 113 episodes.

4. **Verified audio defect versus historical failure.** The installed Storage SDK constructs multipart requests for a File/Blob and uses its own `type`. Its `contentType` option only sets the HTTP content type for non-Blob bodies. Thus `contentType: 'audio/mpeg'` did not correct a valid MP3 File labeled `audio/mp3`. The private bucket permits `audio/mpeg`, not `audio/mp3`. This failure was reproduced with the exact supplied file bytes before changing audio code. Five pre-existing, same-sized MP3 objects for `bpd-1` had no audio metadata references; those indicate separate successful Storage uploads and do not establish why their association failed. Existing objects were preserved. No audio-table/RLS failure was reproduced in the live temporary-record tests. Historical log errors inspected concerned the transcript table, not audiobook persistence.

5. **Exact reproduced error.** `StorageApiError: mime type audio/mp3 is not supported`.

6. **Failing stage.** The reproduced MIME case failed at the direct Storage upload, before database association. The earlier reported failure after upload still needs the authenticated browser error/network response to identify its precise stage.

7. **Fix.** After extension/header/size validation, the upload body is sliced into a Blob with canonical `audio/mpeg` or `audio/mp4` metadata, preserving the original bytes. Both the active direct uploader and legacy Server Action use it. The legacy uploader now uses a unique replacement path with `upsert: false`, rather than overwriting old audio before saving metadata. Database saves independently reload and compare the complete source and optional fields before returning success. Expected errors remain visible, with server-side save diagnostics. Successful uploaded files survive retry; cancel/unmount attempts to remove only unreferenced staged files. Cleanup refuses saved references and logs failures for retry. Old files are removed only after their replacement metadata has saved and confirmed. A browser crash or interrupted cleanup can still leave an orphan; cleanup is best effort, not a transactional Storage/database operation.

8. **Storage architecture.** The active form sends only chapter ID, language, extension, and size to `/api/admin/audio-upload`. Same-origin Admin authorization issues a signed upload token; the browser sends large audio bytes directly to Supabase. New paths are `audiobooks/{chapter UUID}/{ar|en}/{upload UUID}.{mp3|m4a}`. The database stores the stable object path in `book_chapter_audio.storage_path`, never a signed URL. One source is keyed by `(chapter_id, language)`. Legacy Arabic `{chapter UUID}/audio.mp3|m4a` references remain supported. Audio is managed in each chapter's Audiobook tab, not in the book metadata dialog.

9. **Privacy.** The existing `audiobooks` bucket remains private. No public bucket or unrestricted upload/download policy was introduced. Its configured maximum is 52,428,800 bytes (50 MiB); supported audio formats remain MP3/M4A. Anonymous unsigned downloads were denied in live tests.

10. **Playback URLs.** `requestChapterAudio` checks entitlement and authenticated identity, loads the published language-specific source, then generates a signed Storage URL valid for 15 minutes. Stored paths remain stable across URL refreshes. Reader audio controls use the signed URL and offer refresh after playback errors. YouTube sources store normalized IDs instead.

16. **YouTube normalization.** The Admin form and server use the existing `normalizeYouTubeId` helper. Watch URLs, `youtu.be` links, embed/shorts/live URLs, and bare 11-character IDs normalize to the stored ID. Invalid hosts/IDs are rejected. There is no public-search discovery requirement. Visibility cannot be inferred from the URL alone; private videos cannot be made playable for other users by accepting their ID.
